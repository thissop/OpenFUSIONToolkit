# OFT/MUG LM-MHD upgrade execution plan after roadmap review

Prepared 2026-07-01 on branch `lm-mhd-upgrades`.

This note picks up from `OFT_LM_MHD_state_and_roadmap.md` and the attached
"Upgrade roadmap, ranked by effort to impact" excerpt. It incorporates the
new Sophia Guizzo clarification supplied during this run:

- The online standalone 2D MUG solver is compressible and supports fluid
  domains.
- The incompressible LM-MHD formulation is expected in Sophia's merge, not in
  the current online standalone 2D code.
- Wall currents in the coupled plasma/blanket version are expected to come
  through TokaMaker, where finite-element field continuity supplies the current
  closure.
- Hartmann/Shercliff benchmarking has already been done for the online version.
- Reduced/effective Hartmann drag is not central for a standalone channel when
  the Hartmann layers are resolved; it becomes relevant for full-device coupled
  simulations where resolving every Hartmann layer would make the mesh huge.

## 1. Updated strategic answer: is two-way coupling important?

Short answer: yes, but not as the first thing to code blindly.

For a standalone straight channel, two-way plasma/liquid-metal coupling is not
the central missing physics. The applied magnetic field can be treated as given,
the Hartmann layers can be resolved, and the best verification path is exactly
what was already done: analytic Hartmann/Shercliff/Hunt style references and
resolved solver comparisons. In that regime, a reduced drag term is a modeling
shortcut, not a necessity.

For a full-device plasma plus blanket simulation, two-way coupling is
strategically important because it is the unique OFT niche. Standalone duct
codes can solve ducts; OFT can eventually let a time-dependent plasma
equilibrium drive the liquid metal and let blanket currents feed back on the
equilibrium. That matters most for disruptions, VDE-like transients, global
current circuits, electrically connected blanket components, and control or
equilibrium studies where small magnetic perturbations can matter.

The practical ordering is:

1. Do not duplicate Sophia's incompressible solver merge. Treat it as an
   upstream substrate to integrate and verify.
2. Build measurable diagnostics and current-exchange contracts now, so that the
   merge has immediate red-team tests.
3. Prioritize unresolved Hartmann/Shercliff-layer effective drag for
   full-device coupled meshes. Sophia's clarification moves this above
   standalone conducting-wall BC work.
4. Use dimensionless triage to decide when a one-way imposed field is adequate,
   when drag/pressure-drop closure is mandatory, and when two-way field feedback
   should be included.

## 2. Priority ranking after the correction

### P0. Verification and no-hallucination infrastructure

Status: started in this pass.

This includes executable checks for dimensionless identities, HDF5 exchange
schemas, reproducible plotting scripts, and Markdown artifacts that distinguish
measured results from design proposals. This is not glamorous, but it prevents
the failure mode the user explicitly warned about: plausible-looking but
unmeasured results.

Required tests:

- Formula identities: `N = Ha^2/Re`, `Rm = tau_m/tau_u`.
- Source-to-artifact reproducibility: every CSV/PNG regenerated by one script.
- Shape/unit checks on any HDF5 exchange format.
- Red-team labels in every generated result saying whether it is a solver
  result, a formula-level estimate, or a design proposal.

### P1. Effective unresolved Hartmann/Shercliff drag for full-device coupling

Status: highest near-term solver addition after Sophia's clarification.

Why it matters:

- Standalone channel meshes can resolve Hartmann layers, so reduced drag is
  optional there.
- Full-device coupled plasma/blanket meshes cannot afford Hartmann-layer
  resolution everywhere.
- A calibrated effective drag or quasi-2D closure is therefore a practical
  bridge between verified resolved benchmarks and full-device simulations.

Conservative implementation path:

1. Keep the existing `use_wall_drag`, `drag_coeff`, and `drag_bhat` path
   default-off.
2. Add a typed calibration layer rather than hardcoding one disputed formula:
   `drag_model = "none" | "constant" | "hartmann_calibrated" | "sm82"`.
3. Store fitted coefficients and geometry metadata from resolved reference
   cases.
4. Preserve the existing projection behavior: only velocity perpendicular to
   the applied field is damped.
5. Add energy checks: the drag operator must be dissipative for any velocity.

Validation ladder:

- Existing `test_drag_decay`: constant-coefficient backward-Euler decay.
- New local manufactured test: arbitrary velocity vector, arbitrary `drag_bhat`,
  verify only perpendicular kinetic energy decays.
- Resolved-to-reduced calibration: fit alpha from resolved Hartmann/Shercliff
  runs at fixed geometry and compare mean flow/pressure drop, not pointwise
  boundary layers.
- Full-device dry run: turn on calibrated drag only in LM regions where the mesh
  under-resolves `delta_H = a/Ha`.

Red-team checks:

- Do not report pointwise profile agreement from a reduced drag model.
- Do not use one `drag_coeff` across geometries unless calibrated transfer is
  demonstrated.
- Do not claim the closure supplies wall current closure; in the coupled model,
  that belongs to TokaMaker/FE continuity.

### P2. LM current diagnostics and MUG-to-TokaMaker exchange contract

Status: started in this pass with a pure-Python HDF5 schema.

Why it matters:

- Two-way coupling requires a reverse path from LM currents to the equilibrium
  solve.
- Even before a live coupled loop exists, the current output contract can be
  tested independently.
- TokaMaker already has a `vac_solve(..., rhs_source=...)` style interface for
  current sources and field evaluators. The missing piece is projection from the
  LM/MUG current representation to the TokaMaker mesh/source representation.

Implemented first slice:

- `OpenFUSIONToolkit.LM_MHD.CouplingSnapshot` stores `(R,Z)` sample points,
  `(J_R,J_phi,J_Z)` current density, time, optional region ids, optional cell
  volumes, and metadata.
- `write_coupling_snapshot()` and `read_coupling_snapshot()` write/read a
  versioned `/lm_mhd` HDF5 group.
- `toroidal_current_density()` extracts `J_phi`, the component most directly
  relevant to axisymmetric Grad-Shafranov source projection.

Next implementation slice:

1. Add a projection operator from snapshot samples to TokaMaker nodes or cells.
2. Test it on a manufactured toroidal-current distribution with known total
   current.
3. Use `TokaMaker.vac_solve(rhs_source=...)` or the appropriate equilibrium
   source path to compute a magnetic perturbation from the projected current.
4. Compare against an analytic circular-loop or uniform-current sanity case.
5. Only after that, wire into a time-stepping loop.

Red-team checks:

- Enforce units and component ordering in HDF5.
- Check integrated current conservation before and after projection.
- Reject silent nearest-neighbor projection for production use; it is acceptable
  only as a labeled diagnostic prototype.

### P3. Low-Rm inductionless/electric-potential LM mode

Status: still design-level; do not implement casually in the old compressible
module if Sophia's incompressible merge is imminent.

Why it matters:

- For many blanket conditions, magnetic Reynolds number is small even when the
  Lorentz force is dominant.
- An inductionless electric-potential solve removes the need to evolve induced
  magnetic fields for the liquid-metal interior.
- It is the computational unlock for cheap blanket flow in imposed fields.

Governing form to target:

```text
J = sigma (-grad(phi) + u x B)
div J = 0
rho (du/dt + u.grad u) = -grad p + mu laplacian(u) + J x B + ...
div u = 0
```

Boundary/current closure:

- Insulating wall: `J.n = 0`.
- Conducting/coupled wall: closure should be supplied through the coupled
  TokaMaker/FE field representation when available.
- Thin-wall conductance ratios remain useful for standalone benchmark cases,
  but they are no longer the main full-device path if Sophia's TokaMaker
  closure path is the target.

Validation ladder:

- 1D Hartmann insulating channel.
- Shercliff/Hunt side-layer cases already benchmarked by the team.
- Manufactured electric-potential solve with known `phi`.
- Charge conservation: `div J` residual must converge with mesh order.
- Energy budget: `integral J^2/sigma` must match electromagnetic dissipation.

### P4. Coupled driver skeleton

Status: design-level.

Minimal operator-split loop:

1. TokaMaker equilibrium at time `t_n`.
2. Evaluate or export `B(R,Z,t_n)` on LM/MUG quadrature/sample points.
3. Advance LM solver with imposed `B` plus unresolved-layer closure if needed.
4. Export LM current snapshot.
5. Project `J_phi` or equivalent feedback source to TokaMaker.
6. Re-solve equilibrium or vacuum perturbation.
7. Iterate within the timestep only when the feedback metric says it is needed.

The first coupled driver should be a Python-level research driver, not a deeply
embedded Fortran coupling. That makes it easier to red-team every exchanged
field and to compare one-way vs two-way runs.

### P5. Regional and anisotropic materials

Status: medium priority.

This remains important for real blanket geometries, but after Sophia's
clarification it is not the first blocker for wall-current closure. It should
be added where the incompressible/inductionless substrate expects it, not bolted
onto the current compressible standalone module unless a near-term benchmark
requires it.

Validation:

- Region-wise scalar manufactured solution.
- Tensor conductivity manufactured solution.
- Interface current continuity and normal flux checks.

### P6. Standalone conducting-wall Robin BCs

Status: lower than before for full-device coupling, still useful for standalone
Hunt/Shercliff benchmarks.

The previous roadmap treated this as the gateway to wall-current closure. Sophia
clarified that in the coupled version wall currents come from TokaMaker/FE
continuity. Therefore this is no longer the primary two-way coupling route. It
remains valuable for standalone pedagogical benchmarks and code comparisons.

## 4. How to use the new coupling triage artifacts

Regenerate the scan:

```bash
python3 cases/lm_mhd_coupling/two_way_coupling_scan.py
```

Outputs:

- `cases/lm_mhd_coupling/results/coupling_regime_scan.csv`
- `cases/lm_mhd_coupling/results/pbli_regime_heatmap.png`
- `cases/lm_mhd_coupling/results/li_regime_heatmap.png`
- `cases/lm_mhd_coupling/results/two_way_threshold_lines.png`
- `cases/lm_mhd_coupling/results/summary.md`

Default interpretation thresholds:

- `Rm >= 0.1`: question the inductionless assumption.
- `|delta B|/|B_ref| >= 1e-3`: two-way-candidate, run field-feedback
  sensitivity rather than assuming one-way is enough.
- `N >= 1` with low feedback: drag/pressure-drop physics is important even if
  two-way magnetic feedback is small.

The scan found that most of the representative grid is "drag-important" or
"two-way-candidate", not "low". That supports Sophia's point: in full-device
meshes, unresolved Hartmann/Shercliff drag is a near-term practical need even
when the magnetic Reynolds number is small.

## 5. Red-team policy for future results

Every future LM-MHD result should carry these labels:

- `analytic`: closed-form or manufactured reference.
- `resolved-code`: actual MUG/OpenFOAM/etc. run with mesh, tolerances, and
  convergence logs.
- `reduced-model`: closure result calibrated against a resolved reference.
- `triage-estimate`: dimensionless/formula-level scan only.
- `design-proposal`: architecture or code plan with no numerical result.

Forbidden shortcuts:

- Do not report a reduced drag run as a resolved Hartmann-layer profile.
- Do not report a one-way run as coupled plasma/blanket feedback.
- Do not synthesize missing Hartmann/Shercliff/Hunt rows.
- Do not use rounded material properties for design claims.
- Do not claim the current public standalone 2D solver is incompressible.
